# FAT BDOS Characterization Record

This record is the compatibility gate before the FAT-backed BDOS personality
is implemented. `BDOSCHAR.COM` observes ZSDOS through `CALL 5`; it does not
infer directory behavior from third-party application source.

## Utility

Source: `../../Utilities/src/bdoschar.asm`

Build artifact: `../../Utilities/build/bdoschar.com`

Usage:

```text
BDOSCHAR [d:]pattern [d:]output.txt
BDOSCHAR [d:]SETUP
```

Search mode does not change matched files. It replaces the exact output file
named by the second argument, uses a clean 36-byte private search FCB and a
private 128-byte DMA buffer, restores the default DMA at `0080h`, and limits a
search to 64 successful results. Before every SEARCH call it fills DMA with
`A5h`. `SETUP` is separate and deliberately replaces only the reserved fixture
names listed below.

Put wildcard-search reports on another drive so the growing report cannot
become a search result:

```text
BDOSCHAR B:*.* C:BCHAR00.TXT
```

The report is written as sequential 128-byte CP/M records and its final record
is padded with `1Ah`.

## Generated fixtures

The fixture manifest is generated by
`../../Utilities/tools/generate_bdoschar_fixtures.py`. The checked-in generated
table is `../../Utilities/src/bdoschar_fixtures.inc`; `make` verifies that it
has not drifted from the generator.

Copy the current `BDOSCHAR.COM` to a writable conventional drive, then create
the controlled files on the drive under test:

```text
BDOSCHAR B:SETUP
```

`SETUP` creates all files through the running BDOS:

- one exact-name file;
- five `BDWILD??.DAT` matches, without assuming directory adjacency;
- `BDEMPTY.DAT` by MAKE followed directly by CLOSE;
- `BRnnnnnn.DAT` files containing 1, 2, 3, 4, 127, 128, 129, 255, 256 and 257
  sequential 128-byte records;
- four attribute fixtures, with R/O, SYS, ARC and all three set through BDOS
  function 30;
- `BUCOMMON.DAT` in USER 0, 1 and 15, switching through BDOS function 32 and
  restoring the caller's USER afterward.

This ZSDOS system supports USER 0 through 15. The generator rejects fixture
USER numbers outside that range.

The Python generator owns names, USER numbers, record counts and attribute
flags. It emits metadata only; it does not edit a CP/M image or bypass ZSDOS.
Regenerate after changing the manifest with:

```text
make generate-bdoschar-fixtures
```

It also generates `../../Utilities/src/bdoschar.sub`. With `BDOSCHAR.COM` and
`BDOSCHAR.SUB` on B:, reports on C:, and `SUBMIT` available, run the complete
matrix from USER 0 with:

```text
SUBMIT BDOSCHAR
```

The generated submit file performs both default-drive and explicit-drive
searches, exhausts every wildcard search, repeats `BUCOMMON.DAT` under USER 0,
1 and 15, and ends in USER 0. USER-specific reports are written to the same
USER on C:. Every invocation includes the changed-caller-FCB phase.
Generator options `--program-drive`, `--fixture-drive`, and `--output-drive`
can produce a different mapping.

RunCPM was used to verify fixture creation, sequential record sizes, searches,
and report-file output. Its host-directory BDOS does not expose function-30
attributes. The target-ZSDOS capture below validates those attribute bits and
the generated SUBMIT sequence.

Each result is emitted as hexadecimal records:

```text
CALL=SF INDEX=00 A=00
FCB=<36 bytes>
DMA=<128 bytes>
SLOT=00 DATA=<32 bytes>
```

`SLOT` appears only when returned `A` is `00h` through `03h`. The second phase
fills the caller's original search FCB with `CCh` after SEARCH FIRST and then
calls SEARCH NEXT. This directly tests whether continuation depends on the
caller preserving that FCB.

## Controlled fixture matrix

Capture the complete output for each applicable row on a conventional
ZSDOS-backed drive:

| Case | Fixture / invocation | Evidence sought |
|---|---|---|
| Exact name | `BDOSCHAR B:BDEXACT.DAT C:BCHAR01.TXT` | return slot and exact entry fields |
| Wildcard | `BDOSCHAR B:BDWILD??.DAT C:BCHAR02.TXT` | packed eleven-byte `?` matching |
| Multiple matches | the five generated `BDWILD??.DAT` files | slot `0..3`, sector reuse, SEARCH NEXT order without assuming physical adjacency |
| End of search | any finite pattern | failing return and untouched/changed DMA bytes |
| Empty file | `BDOSCHAR B:BDEMPTY.DAT C:BCHAR03.TXT` | EX/S1/S2/RC and allocation bytes after MAKE/CLOSE with no write |
| Extent sizes | `BDOSCHAR B:BR??????.DAT C:BCHAR04.TXT` | EX/S2/RC progression by sequential record count |
| Attributes | `BDOSCHAR B:BAATTR?.DAT C:BCHAR05.TXT` | high attribute bits set through function 30 |
| USER | repeat `BDOSCHAR B:BUCOMMON.DAT C:BCHARUxx.TXT` in generated USER 0, 1 and 15 | directory-entry user byte and isolation |
| Default drive | from B:, `BDOSCHAR BDEXACT.DAT C:BCHAR06.TXT` | FCB drive zero behavior |
| Explicit drive | `BDOSCHAR B:BDEXACT.DAT C:BCHAR07.TXT` | explicit drive behavior |
| Changed caller FCB | automatic second phase | SEARCH NEXT dependence on the original FCB |

Wildcard-drive coverage is intentionally omitted; it has no current
compatibility requirement.

Directory entry byte offsets used when interpreting `DATA` are:

| Offset | Meaning |
|---:|---|
| 0 | USER |
| 1-8 | filename and attribute high bits |
| 9-11 | extension and attribute high bits |
| 12 | EX |
| 13 | S1 |
| 14 | S2 |
| 15 | RC |
| 16-31 | allocation block bytes |

## Captured result

The target-ZSDOS reports are stored verbatim under
[`characterization/zsdos-bdos-search`](characterization/zsdos-bdos-search/).
The capture identifies drive B as `01h` and covers USER 0, 1 and 15. The exact
ZSDOS build identity was not recorded with the reports.

The reports establish this SEARCH FIRST / SEARCH NEXT behavior:

- Success returns `A=00h` through `03h`. The value selects one of four 32-byte
  directory entries in the 128-byte DMA sector.
- ZSDOS writes the whole physical directory sector to DMA. Entries other than
  the returned slot may be unrelated, deleted, or owned by another USER.
- End of search returns `A=FFh`. DMA is not preserved: despite being filled
  with `A5h` before the call, it contains the final directory sector scanned.
- SEARCH FIRST changes caller FCB byte 13 (S1) to `80h | USER`; it leaves the
  caller's drive and packed name intact. SEARCH NEXT leaves that value in
  place.
- SEARCH NEXT state is internal to ZSDOS. Overwriting all 36 bytes of the
  caller FCB with `CCh` after SEARCH FIRST does not alter the next returned
  match. `BCWILD.TXT` demonstrates this with a second successful result.
- Default-drive and explicit-drive FCBs return the same directory entry. The
  default FCB retains drive byte zero; the explicit FCB retains drive byte two.
- USER filtering selects only the current USER's matching entry even when DMA
  also contains entries belonging to other users.

The attribute reports encode R/O, SYS and ARC in the high bits of extension
bytes 9, 10 and 11 respectively. The combined fixture has all three high bits
set. The empty file reports `EX=00h`, `S1=00h`, `S2=00h`, and `RC=00h`.

The record-count fixtures produce these directory extent fields; S1 and S2
are zero in every selected entry:

| File records | Returned `(EX, RC)` entries |
|---:|---|
| 1, 2, 3, 4 | `(00h, 01h)`, `(00h, 02h)`, `(00h, 03h)`, `(00h, 04h)` |
| 127 | `(00h, 7Fh)` |
| 128 | `(00h, 80h)` |
| 129 | `(01h, 01h)` |
| 255 | `(01h, 7Fh)` |
| 256 | `(01h, 80h)` |
| 257 | `(01h, 80h)`, then `(02h, 01h)` |

The 257-record file therefore returns two matching directory entries. The
allocation bytes contain conventional-disk block numbers and have no FAT
meaning.

The FAT-backed facade will use this synthetic SEARCH contract:

```text
on match:
    DMA[0..127] = E5h
    DMA[0..31]  = synthetic directory entry
    A           = 00h

on exhaustion:
    A           = FFh
    DMA         = unspecified
```

The selected entry contains only the required USER, seven-bit-clean packed 8.3
name, EX, S1, S2 and RC fields. FAT attributes are not mapped into CP/M name
high bits. Bytes 16 through 31, the allocation fields, are zero. The other
three DMA slots have no meaningful entries. The FAT personality returns one
entry per file whose `EX`, `S2`, and `RC` describe its terminal logical extent;
function 35 supplies the complete record count. This retains the size metadata
used by catalogue tools without inventing multiple physical CP/M extents, which
caused directory programs to display a large FAT file repeatedly.

For SEARCH FIRST with FCB drive byte `3Fh` (`'?'`), the FAT personality follows
the CP/M raw-directory convention. It searches the current drive across USER 0
through 15, continues across USER namespaces through SEARCH NEXT, and returns
the source USER in each synthetic entry. Missing `@N` directories are empty.

The raw end-of-search sectors contain a `BUCOMMON.DAT` entry with user byte
`1Fh`. This was created by the earlier fixture generator passing 31 to BDOS
function 32. USER 31 is not supported by this ZSDOS system, so that entry is
an invalid test artifact and is excluded from the compatibility contract.
