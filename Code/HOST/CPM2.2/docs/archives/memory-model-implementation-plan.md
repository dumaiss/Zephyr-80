# Memory Model — Implementation Plan

How to execute the placement work in
[entity-placement-gap-analysis.md](entity-placement-gap-analysis.md). That
document is the *what and why*; this one is the *order, and how each step is
proved*.

**Scope.** Sections 4, 5, 6 and 7 of the analysis: moving misplaced code out of
common memory, zoning what remains, putting drivers in slots, and making
drivers relocatable. The source reorganization (analysis section 8) is
deliberately **out of scope** — it renames files without moving bytes, and
mixing a rename pass into an address pass makes both unreviewable.

---

## 1. Ground rules

Every step in this plan is a separate change with its own build and its own
review. None of them is combined.

1. **One placement change per step.** Never a placement move and a behavior
   change together.
2. **Build after every step**, and read the generated map — do not assume it.
3. **Run `make test` after every step.** All three qkz80 harnesses.
4. **Stop at the end of each phase.** Do not roll into the next one because the
   last step went well.
5. **Every step is revertible on its own.** If a step needs a later step to
   work, the sequence is wrong.

## 2. The review artifact

`docs/memory-map.md` is generated by every build **and tracked in git**. After
each step:

```sh
make && git diff docs/memory-map.md
```

That diff is the review. It shows exactly which regions moved, by how much, and
what happened to the free space — which is precisely the question each step has
to answer. A step whose map diff contains something unexplained is a step to
revert, not to investigate afterwards.

`make test` covers the interrupt core, the FAT BIOS and the FAT BDOS
personality. `check_overlap.py` catches any byte emitted twice, and
`check_diag_record.py` catches drift against the Utilities mirror. All three run
inside `make`.

## 4. Constraints discovered while planning

These were found by tracing call sites and they **change the analysis's
arithmetic**. Section 4 of the analysis says the SIO core has 385 movable bytes.
It has fewer.

### 4.1 Boot calls the SIO core before bank 7 is trusted

`cbios_boot.asm` runs in mode 11 from its first instruction, but:

```asm
	call sio_core_init
	; Nothing in bank 7 may be called until it is known to hold this build's
	; image.  The check reports over SIO0/B, which is common, and halts.
	call bank7_check
```

So `sio_init` and `sio_core_init` (`F2F0h-F321h`, 50 bytes) **cannot move to
bank 7**. They run before the bank-7 image is validated, and moving them would
mean executing unverified bank-7 code to produce the diagnostic that reports
bank 7 is bad.

Note the distinction the existing design already makes: the boot *stack* is in
bank 7 at `C000h` before the check, because a corrupt bank still works as RAM.
Code is different.

### 4.2 The bank-7 failure path needs `sio_send_byte`

`bank7_check_failed` emits its message with:

```asm
	ld a,#SIO_CH_CONSOLE
	call sio_send_byte
```

So `sio_send_byte` (`F3C9h-F401h`, 57 bytes) must stay in common as well, unless
that failure path is given a minimal inline TX loop of its own (roughly 15
bytes, polling TX-empty with no channel selection, CTS handling or timeout).

**Decision point.** Leave `sio_send_byte` in common, or inline the failure
emitter and reclaim 57 more bytes? Recommendation: leave it for now. The
headroom below is sufficient without it, and the failure path is the one piece
of code that must work when everything else is broken — it is a poor place to
economize.

### 4.3 Revised arithmetic

| | Analysis said | Actually |
|---|---:|---:|
| banner printer | 56 | 56 |
| SIO core, movable | 385 | **~278** (`sio1_ioc_init`, `sio_register_rx_sink`, `sio_recv_byte`, the IOC RTS/put/get helpers, `sio_rx_kick`) |
| SERCON, movable | 211 | 211 |
| **total reclaim** | **652** | **~545** |

Which gives:

```text
common code after   3477 - 545 = 2932
contiguous headroom 5120 - 2932 - 1440 = 748
less a 384-byte Z4  364
```

Still far better than 203 bytes in seventeen crumbs, and still enough for the
VDrip ISR tail. The analysis's sections 4 and 6.5 should be corrected to these
numbers.

The `~278` carries a tilde deliberately: it assumes every routine between
`sio1_ioc_init` and `sio_rx_kick` is called only after `bank7_check` and only
from outside an ISR. **Step 2.1 begins by confirming that per routine.**

One step, chosen because it exercises the entire loop at the smallest possible
risk.

## 7. Phase 3 — the relocation mechanism

Nothing moves in this phase. It changes how the build computes addresses.

### Step 3.1 — symbol extraction from the linker map

| | |
|---|---|
| **Change** | `generate_memory_docs.py:parse_listing()` currently reads final addresses from `build/firmware.lst`. Add map-based extraction and switch the callers to it. |
| **Why first** | It feeds the documentation generator *and* all three qkz80 harnesses. Relocatable areas make listing addresses area-relative, so this must work before any area is converted. |
| **Verify** | The strongest check available: **`docs/memory-map.md` must not change at all**, and `make test` must pass unchanged. A pure re-plumbing that alters one address is wrong. |

### Step 3.2 — convert one driver to a relocatable area

| | |
|---|---|
| **Change** | The A: backend: `.area DRV_STORAGE_A (REL)`, drop its `.org`, place it from the Makefile with `-b DRV_STORAGE_A=0x4330`. |
| **Why this one** | Small (164 bytes), already configuration-selected, and has two implementations to prove the mechanism against. |
| **Verify** | Placed at the same address as before ⇒ **byte-identical image** against the Phase 2 baseline. Then deliberately place it 256 bytes higher, confirm the map moves and the image still boots, and put it back. |

### Step 3.3 — convert the remaining drivers

One per commit, each verified byte-identical at its current address first.

Stop.

## 8. Phase 4 — zones and slots

### Step 4.1 — declare the zones, reporting only

Add `zone` and `source` fields to `Region`. Emit a report; **do not fail the
build yet.** Confirm the report matches reality after Phases 1-2.

### Step 4.2 — reorganize common memory

Code grows up from `EC00h` (Z1 ABI, Z2 crossing, Z3 interrupt, Z4 driver
slots), state grows down from `FFFFh`, one headroom block between. The TPA is
not touched: `E000h-EBFFh` stays application-owned, and the transient program
area remains `0100h-EC05h`.

Consolidating the three IRQ code islands (`FC98h`, `FCE0h`, `FF60h`, 206 bytes)
into Z3 happens here.

### Step 4.3 — declare Z4 and place the sinks

Size Z4 for the largest ISR tail. **Gated on a decision:** 384 bytes if the
VDrip sink keeps parsing inline, or ~128 plus a queue if the sink is first
fixed to enqueue and return, as the project's own SIO rule requires. Settle
this before writing the constant.

### Step 4.4 — bank-7 slots

Fixed granules with reserved headroom, each driver carrying its private state.
Budget: ~26 KiB of slot space against ~14.5 KiB of drivers.

### Step 4.5 — tighten the assertion

Switch the zone check from reporting to failing. This is the step that stops
the whole problem recurring, and it goes last because everything before it has
to be true first.

Stop.

## 9. Phase 5 — the payoff

### Step 5.1 — generalize the transport-linked condition

`VDRIP_TRANSPORT_LINKED` currently follows `CONSOLE` alone. Make it
`CONSOLE=vdrip` **or** `STORAGE_A=vdrip`, and delete the Makefile error that
rejects `STORAGE_A=vdrip` with a non-VDrip console. SERCON's existing
`.ifeq VDRIP_TRANSPORT_LINKED` guard already expresses the SIO0/B sink
exclusivity correctly and needs no change.

### Step 5.2 — restore `CONSOLE=vdrip`

With the transport split (2.4) and Z4 declared (4.3), place the 357-byte ISR
tail and build. This proves Phase 2.4, which could not be verified when it was
made.

### Step 5.3 — the combination matrix

Build and boot all four `CONSOLE` × `STORAGE_A` combinations. This is the
acceptance test for the whole plan: *every combination that makes sense builds.*

## 10. What this plan does not do

- **No source reorganization.** Analysis section 8, deliberately separate.
- **No interface changes.** De-VDripping the console backend contract travels
  with the source work, not with this.
- **No memory manager.** Analysis section 6 concluded the common data region has
  no dynamic demand to serve; the one cheap item there — an "in use" byte
  guarding the 512-byte staging arena — is worth doing but is a behavior change
  and belongs on its own.
- **No relocation-driven packing.** Slots stay fixed-size; relocation is the
  mechanism for changing slot assignments cheaply, not a licence to pack
  end-to-end.

## 11. Order of the decisions this plan needs

| Decision | Gates | Recommendation |
|---|---|---|
| Inline the bank-7 failure emitter? | step 2.2 sizing | No — leave `sio_send_byte` common |
| Fix the VDrip sink to enqueue-only? | step 4.3, Z4 size | Yes, but as its own change, before 4.3 |
| Slot granule: 512 bytes or 1 KiB? | step 4.4 | 512; the population's small end wastes most of a 1 KiB granule |

Each can be deferred until the step that needs it, except the second, which is a
behavior change and should not be bundled into a placement step.

#### The third constraint: `sio_rx_kick` and `irq_sink_context` are mutually recursive

```text
sio_rx_kick                     F43Dh, common
  SIO_RX_KICK_CONSOLE
    call sio_core_rx_lock       F471h  -- ISR block, stays
    call irq_sink_context       FC98h  -- common IRQ policy region
         call SIO_RX_KICK_READ  F45Fh  -- back inside sio_rx_kick's own body
              call sio0b_clear_rx_error   F4C0h -- ISR block, stays
              jp   sio_core_dispatch_rx   F4D2h -- ISR block, stays
```

`irq_sink_context` is the polling-sink entry in the IRQ policy region: it runs
masked and saves the full index/alternate context precisely because it stands in
for an ISR frame. `sio_rx_kick` is therefore not ordinary foreground code that
happens to sit near the ISR — it is part of the receive machinery, it is
re-entered from common interrupt-policy code, and three of its four calls land
in the ISR block. It stays.

### Phase 3 — 3.1 done, 3.2 blocked. Decision needed.

Hardware confirmed step 2.3 (serial console tee, ESC-ESC-ESC gesture).

**Step 3.1 — symbol extraction, done, but not as planned.** The plan said "move
extraction to the linker map." That is impossible: the ASxxxx symbol table
**truncates names to eight characters**.

```text
622 truncated names, 285 of them ambiguous
fat_nati x79   ZNATIVE_ x37   fat_sear x33   SD_STORA x32
```

Nine different `sio_core*` symbols collapse to `sio_core`. The map cannot
identify a symbol, which is why `gen_zsdos_bios.py` has always used a
prefix-plus-ambiguity-check for its three lookups.

The right source is the linker's **updated listing**, `sdldz80 -u`, which
rewrites the `.lst` as `.rst` with resolved addresses and full names. It is a
drop-in: `parse_listing` needed no change at all.

```text
lst symbols 2016   rst symbols 2016   differing 0
```

Applied: `LDFLAGS += -u`, and the doc generator plus all three harness runners
now read `build/firmware.rst`. Verified — `docs/memory-map.md` byte-identical,
`build/zephyr80.bin` byte-identical, `make test` 3/3 PASS. The only change to a
generated document is the provenance line naming the file that was read.

**Step 3.2a — every `.org` now declares its area.** Seven `.org` directives
inherited whatever area happened to be current (`cbios_irq.asm` x3,
`cbios_iocall.asm`, `cbios_xing.asm`, both storage backends). Harmless while
everything is ABS; fatal the moment one area is REL. Each now carries the
explicit `.area` that governed it. Verified byte-identical.

**Step 3.2 — reverted. Relocatable areas do not work in this build's shape.**

Converting the A: backend to `.area DRV_STORAGE_A (REL)` links it correctly —
`-b DRV_STORAGE_A=0x4330` places it exactly where the `.org` did — but the
image then extends to `0x143601` and `makebin` fails.

Cause, from the linker map:

```text
original build      59 areas, ALL ABS,  0 REL
one REL area added  29 areas became REL

DRV_STORAGE_A   4330h      164 bytes  (REL,CON)
WORK1d          43D4h   24 607 bytes  (REL,CON)
WORK1e          A3F3h   24 850 bytes  (REL,CON)
WORK1f         10505h   65 093 bytes  (REL,CON)
```

The REL attribute propagates to the auto-numbered areas that `.org` creates
after it, and the linker then chains them consecutively instead of honouring
their origins. One relocatable area contaminates everything following it.

This is structural, not a flag error. In a single translation unit whose layout
is expressed as ~59 `.org` directives, relocatable areas and absolute origins
cannot coexist.

#### The decision

| Option | What it costs |
|---|---|
| **A. Drop relocation.** Keep ABS + `.org`; a slot reassignment stays a constants edit. | Phase 4's slots work unchanged — they are declared limits, not relocation. Loses only the *convenience* of re-slotting. |
| **B. Separate translation units.** Assemble each driver to its own `.rel` and link them, which is how REL areas are meant to be used. | A real build change, and it overlaps heavily with the source reorganization (analysis section 8) that is out of this plan's scope. |
| **C. Express the whole layout as named areas placed by `-b`,** dropping `.org` entirely. | Rewrites the layout mechanism wholesale. Not proportionate. |

**Recommendation: A for now, B later with the source reorganization.** Nothing
in Phase 4 needs relocation — fixed slots are declared bases and ceilings, which
ABS already provides, and the two bank-7 regions added in Phase 2 already
demonstrate the pattern. Relocation only makes *changing* a slot assignment
cheaper, and that is a convenience worth having at the same time as B, not
before it.

What step 3.2 bought even though it was reverted: the knowledge that this is
structural, obtained from one 164-byte driver instead of after converting eight,
plus 3.2a, which removes a latent hazard regardless.

**Phase 3 leaves in place:** `-u`/`.rst` extraction (3.1) and explicit areas
(3.2a). Both verified byte-identical. Nothing to test on hardware — the image
has not changed since the 2.4 build that was already confirmed.

**Decision taken: option A.** Relocation is dropped from this plan. Phase 4
proceeds with `ABS` and `.org`, which is all that fixed slots require. Option B
— one translation unit per driver, which is what makes `-b` placement work — is

**Step 4.2 — computed, not applied.** Code up from `EC00h` in zone order, state

**Step 4.2b — the reorder itself. Not attempted; one design correction first.**

Section 6.3 of the analysis promises "one headroom block". With Z4 at 384 the
code run ends at `F8F5h`, leaving 663 bytes before the 1440-byte state block —
but the state block cannot be packed densely, because the IM2 vector page must
sit on a 256-byte boundary and its guard byte must immediately follow it:

```text
IM2 at FD00h, state at FA60h:  672 bytes below the page, 511 above
                               staging 512 + facade copies 320 = 832 > 672
                               and 671 bytes of the rest > 511    -- no fit

IM2 at FC00h, state at FA00h:  staging 512 fills FA00h-FBFFh exactly
                               guard FD00h, the remaining 671 bytes fit above
                               with 96 spare                       -- fits
```

So the realistic outcome is a **267-byte contiguous headroom plus ~96 bytes of
alignment slack inside the state block**, not a single 363-byte block. Still far
better than today's sixteen fragments whose largest is 214, but the analysis's
section 6.5 overstates it and should say so.

That is a design detail worth settling before the addresses are rewritten,
which is why 4.2b stops here rather than guessing.

**Step 4.2b — stopped before editing. It is not the change this plan described.**

The plan calls 4.2 "reorganize common memory," implying a rewrite of region base
constants. Inspection says otherwise. The layout is not a table that can be
reordered; it is a scheme spread through `cbios_defs.inc`:

```text
line  127  CBIOS_NATIVE_GATE_BASE   = 0xefc2
line  613  CBIOS_BASE               = 0xf000
line  654  CBIOS_BANKING_CODE_BASE  = CBIOS_BASE + 0x01b0
line  825  CBIOS_SPARE_CODE_BASE    = CBIOS_BASE + 0x0288
line  982  CBIOS_SIO_CORE_CODE_BASE = CBIOS_BASE + 0x02f0
line 1051  CBIOS_SERCON_CODE_BASE   = 0xf830
```

Sixteen code bases across ~900 lines, half of them expressed as
`CBIOS_BASE + offset` — so they cannot be reordered independently without first
abandoning that expression — each embedded in a block of commentary explaining
why it sits where it does, most of which becomes false on the move. The state
block adds ~30 more constants, including vestigial aliases from the flat design
(`CBIOS_SCRATCH_*`, `CBIOS_DRIVER_SLOT5_*`, `RESERVED_*`) that still resolve to
live addresses, plus moving the IM2 vector page and changing the `I` value.

That is a rewrite of the layout module, not a placement edit, and it is the
riskiest single change in this plan. It should not be done as a continuation of
a long session; it wants its own pass with a constant-by-constant map reviewed
before anything is built.

#### A cheaper route to most of the value

The reorder exists to serve step 4.5 — making the zone rule something the build
enforces. But enforcement does not require contiguity. Two separable ideas:

| | What it asserts | Cost |
|---|---|---|
| **Classification** | every region declares a zone, and no region sits in a memory class its zone forbids (a `driver` in common must be ISR-reachable; `core` may not be in common at all) | none — the `zone` field exists, `ZONE_BOUNDS` just needs per-class *predicates* instead of address ranges |
| **Contiguity** | zones occupy disjoint contiguous address ranges | the full reorder above |

Classification is what stops the drift that produced this document. Contiguity
buys one consolidated headroom block — and with Z4 reserved at 384 the VDrip
tail is already housed, so nothing currently needs it.

**Recommendation:** implement classification enforcement as step 4.5 now, and
treat the contiguity reorder as optional work to be scheduled on its own. The
card castle is already fixed (4.2a): every region has its own declared ceiling,
so slack is reserved rather than inherited, which was the actual defect.

**Step 4.5 — classification enforced.** Implemented as predicates rather than
address ranges, per the recommendation above. Every region declares a zone, and
the build refuses any region whose zone is not permitted in its memory class:

```text
common   abi | crossing | interrupt | driver-isr
bank 7   core | driver  | state     | asset
```

`core` is deliberately absent from the common set: core defines contracts and
has no reason to be addressable under more than one latch state.
`crossing`/`interrupt` are absent from bank 7 for the mirror reason. A driver
appears in common only as `driver-isr`, which forces "which part of this driver
does an interrupt reach?" to be answered in the declaration rather than in
someone's memory. The SERCON sink is retagged accordingly.

Mutation-tested — each of these fails `make` with a named error:

```text
common region tagged core        ERROR: common SIO ownership return: zone 'core'
                                 is not permitted in common
SERCON sink tagged plain driver  ERROR: common Serial console: zone 'driver'
                                 is not permitted in common
zone removed from a region       ERROR: bank 7 SIO services (bank 7):
                                 declares no zone
```

Image byte-identical; `make test` 3/3.

The contiguity reorder is recorded as step 6 of the source-reorganization
migration in `entity-placement-gap-analysis.md` section 8.5, with the four
measured obstacles, and marked as worth ~64 bytes of extra contiguous headroom —
a tidiness change, not a capacity one.

### Step 5 — one translation unit per driver: pilot done, and a caution

**Prerequisite: `build/config.inc`.** The two feature flags lived inside
`zephyr.asm` and were rewritten by `sed`, which only works while there is
exactly one translation unit. They are now a generated header every unit
includes. Byte-identical.

**Prerequisite: CP/M constants moved to the layout header.** `CBASE`, `FBASE`,
`IOBYTE` and `TDRIVE` were defined in `zephyr.asm`. They are assembly-time
constants, so the linker cannot resolve them across units — every unit needs the
same definition. Now in `layout/memory.inc`, which is also where the Makefile
reads `CBASE` from to build ZCPR2.

**Pilot: the A: backend.** `drivers/storage/rom.asm` and
`drivers/storage/vdrip.asm` each assemble to their own `.rel` and link in. The
`STORAGE_A` choice is now a **link input** rather than a rewritten `.include`:

```make
DRIVER_REL_STORAGE_A ?= $(BUILD_DIR)/drv_storage_$(STORAGE_A).rel
$(FIRMWARE_IHX): $(FIRMWARE_REL) $(DRIVER_RELS)
	$(SDLDZ80) $(LDFLAGS) $@ $(FIRMWARE_REL) $(DRIVER_RELS)
```

Symbol symmetry needed no work — the files already carried full `.globl`
blocks from when they were conceptually modules.

Tooling that had to follow: `sdldz80 -u` writes one resolved listing per unit,
so `parse_listings()` now merges them and the generator, the Makefile and all
three harness runners take a list.

Default image byte-identical, `make test` 3/3, `STORAGE_A=vdrip` assembles.

#### The caution

This step has produced a third distinct asxxxx area/`.org` hazard, and they are
all the same shape — the layout idiom is coupled to single-unit assembly:

| | Symptom | Found by |
|---|---|---|
| `.org` inherits the ambient area | fatal only once some area is REL | step 3.2a |
| one REL area turns 29 of 59 areas REL | image runs past 64 KiB | step 3.2 |
| re-entering an ABS area makes the next `.org` **relative** | `storage_caller_sp` silently moved `FE68h -> FE6Ch`, and three call sites followed it | this step |

The third is the worrying one: it produced a *correct-looking build with wrong
addresses*, caught only by the byte-identical check. The fix is to give each
`.org` block its own area name rather than re-entering one.

**Before converting the other eight drivers, every re-entered `.area ... .org`
pair in the tree should be audited**, because each is a latent silent move. The
pilot found two (both A: backends); there are likely more.

A second, procedural note: three times in this work a build failed while
`cmp` still reported the image identical, because `make` had left the previous
artifact in place. `cmp` alone is not proof — the build's exit status has to be
checked in the same breath.

every unit that uses one needs the same definition. These moved to
`layout/platform.inc`: `SIO_RX_READY`, `SIO_TX_READY`, `SIO_RR0_CTS`,
`SIO0B_DATA_PORT`, `SIO0B_CTRL_PORT`, `SIO0B_WR5_RTS_OFF/ON`; and to
`layout/memory.inc`: `CBASE`, `FBASE`, `IOBYTE`, `TDRIVE`. One,
`SIO_RR0_CTS`, had been **defined twice** with the same value in two files —
which a single unit silently tolerated.

**Exports lost in the earlier splits.** When a file was split at its ISR
boundary, the `.globl` block went with one half. The other half then defined
symbols nothing exported. Both halves now declare what they export and what they
import, which is the discipline multiple units force and a single unit does not.

**Area namespacing.** asxxxx concatenates same-named areas across objects, so a
second unit's `CODE (ABS)` starts after the first unit's and its `.org` becomes
relative. Every driver unit now namespaces its areas (`V9958_CODE`,
`ROMDSK_WORK`, ...). This is the generalization of the `storage_caller_sp` bug,
and `check_org_placement.py` is what makes it safe to have discovered late.

#### New build check: `tools/check_org_placement.py`

Compares, for every `.org <symbol>` in the resolved listings, the address the
assembler assigned against the symbol's value. 54 sites, all agreeing. It fired
on the very next conversion after being added, catching the HID driver's two
`.org`s landing 164 and 78 bytes late:

```text
check_org_placement: ERROR - .org did not land on its constant:
  drv_console_hid_input.rst: .org CBIOS_HID_INPUT_CODE_BASE placed at 3DA4h,
    but CBIOS_HID_INPUT_CODE_BASE = 3D00h (off by +164)
  Cause: re-entering an ABS area makes the following .org relative.
  Fix:   give the block its own .area name instead of re-entering one.
```

Mutation-tested by reintroducing the original `storage_caller_sp` bug.

#### Relocation is now possible, and still not done

Step 5's purpose was to make `-b AREA=addr` placement work, and the blocker —
one REL area contaminating every area after it — was a consequence of single-unit
assembly. With one unit per driver that no longer applies. Converting a driver's
area to `REL` and placing it from the Makefile is now a small, testable change
per driver. It is not attempted here: the units landed byte-identical and that is
the right place to stop.

### Step 5's second half — relocation: possible now, and not worth doing

The translation-unit split removed the blocker. A driver's area can be made
`REL` and placed with `-b AREA=addr`. Measured before attempting it:

```text
32 .org sites across the nine driver units
   sd 9 · rom 5 · vdrip storage 5 · ioc_command 3 · hid 2 · v9958 2
   vdrip console 2 · fat 2 · sercon 1 · vdrip transport 1
```

Each distinct `.org` needs its own `REL` area and its own `-b` flag, so the
conversion is ~32 area splits plus a generator that emits the `-b` list.

The question is what the build would gain, and under the slot design the answer
is nothing:

```text
today   layout/memory.inc declares CBIOS_STORAGE_A_CODE_BASE
        drivers/storage/rom.asm does .org CBIOS_STORAGE_A_CODE_BASE

after   layout/memory.inc declares CBIOS_STORAGE_A_CODE_BASE
        a generator reads it and emits -b ROMDSK_CODE=<that value>
```

Section 7.3 of the analysis justified relocation as *"change one number in the
Makefile"*. But the address authority is `layout/memory.inc` — deliberately, and
the whole reorganization reinforced it — so changing a slot is editing one
constant there either way. Moving the placement table into the Makefile would
mean two authorities for addresses, which is the drift this project already
guards against with `check_diag_record.py` and the generated `CBASE`.

The one capability `REL` genuinely adds is **linker-assigned packing**, and
fixed slots were chosen over packing deliberately (section 7.2).

**Conclusion: relocation is unblocked but not worthwhile while slots are fixed.**
It is recorded as available should packing ever become the right trade — that is
the day bank 7 gets tight, and the ratio is 1.8 today. The translation-unit split
earned its keep on its own: it removed the `sed` step, exposed a duplicated
constant and several lost exports, and made the per-file memory-class check
possible.

### Small correction

`generate_memory_docs.py` labelled the synthetic FAT DPH, DPB and allocation
vector as `D:` in three places. `FAT_BIOS_DRIVE = 0x01`, which is `B:`, and the
drive dispatcher routes C:/D: to SD units. The generated map said `D:` for a
structure belonging to `B:`. Corrected; documentation text only, image
byte-identical.

### Step 7 — the video contract no longer speaks Virtual Drip

`src/core/video_ops.inc` now declares what a display backend implements:

```text
VIDEO_OP_CTRL_WRITE  VIDEO_OP_DATA_WRITE   VIDEO_OP_DATA_BLOCK
VIDEO_OP_PALETTE_WRITE  VIDEO_OP_INDIRECT_WRITE
VIDEO_OP_RESET  VIDEO_OP_PRESENT  VIDEO_SINGLE_PAYLOAD_MAX
```

`core/video_send.asm`, `drivers/console/v9958.asm` and `common/gates.asm` use
those names; the V9958 driver's private copy of the numbering is deleted. A
driver for a new video card now implements `VIDEO_OP_CTRL_WRITE`, not "Virtual
Drip packet type 01h".

**The byte values are unchanged and stay frozen**, because BDOS function 215
takes that byte and the HelloWorld demos are compiled against it. What changed
is that the numbering is an ABI detail of one header instead of a vocabulary
every backend has to learn and re-declare. Image byte-identical, `make test`
3/3, `CONSOLE=vdrip` still assembles.

Why not a fully neutral renumbering: the two backends have different contracts
today. The V9958 backend switches on a closed set and rejects the rest; the
Virtual Drip backend is **transparent** — `vdrip_send_frame` stores whatever
type byte it is given and frames it, so a program can send `PACKET_COMMAND_STREAM`
(`1Ah`, which the mandelbrot demo does) or `PACKET_VDP_SCROLL` through it.
Closing the set would narrow what function 215 accepts on a VDrip console, which
is an ABI narrowing and not something a cleanup pass should decide.

**What remains of the debt**, and both are behaviour changes needing a hardware
run:

- `VIDEO_SINGLE_PAYLOAD_MAX` is a Virtual Drip frame size enforced in
  `VIDEO_SEND`, above the contract, so it caps a directly attached chip that
  could take more. It should be something a backend declares.
- The transparent-versus-closed difference between the two backends is
  undocumented in the contract. Either the contract admits a pass-through
  operation, or function 215's accepted set is narrowed deliberately.

#### A regression the sweep caught

### The common reorder, attempted and reverted — with its blockers now known

Restoring `CONSOLE=vdrip` needs 357 contiguous bytes in common for the
transport's interrupt half. There is no cheaper placement: the largest free run
is 214 bytes, and in a VDrip build the unused serial-console region gives 296.
Splitting a byte-at-a-time state machine across two holes to save 37 bytes is
not a trade worth making, so the free space has to be consolidated.

A **targeted** consolidation is enough — the full zone reorder is not needed.
Moving the four regions that sit between the two holes merges them:

```text
F2F0h  SIO core            330 used of 336
F440h  crossing layer       26 of 32
F460h  transport level       1 of 8
F468h  crossing gates      476 of 488
F650h  interrupt dispatch  238 of 248
F748h  COMMON DRIVER SLOT  384 reserved -- VDrip's tail is 357, SERCON's 84
F8C8h  headroom            144
```

Twelve constants. It assembles, links, and passes `check_overlap`,
`check_diag_record` and `check_org_placement`. It was reverted anyway, because
it fails `make test` with *"ISR failed to return"*, and the reason is a
constraint worth writing down.

**Blocker 1, solved: `ROM_ACCESS_BASE`.** The crossing layer straddles a
seven-byte primitive that the image builder mirrors into every ROM page's tail,
so instruction fetches continue in ROM after the latch switch. It looked pinned;
it is not. The builder's only rule is
`ROMDISK_PAGE_BYTES <= ROM_ACCESS_BASE < 64 KiB`, so it may move anywhere in a
page tail as long as it keeps its offset within the crossing layer. Moved to
`F452h`; all checks pass.

**Blocker 2, unsolved: the IM2 `FFh` vector is a palindrome.** An unclaimed bus
supplies vector `FFh`, whose pointer is fetched from `FDFFh` and `FE00h`. `FDFFh`
is the high byte of the vector page's last entry — `irq_unexpected` — and `FE00h`
is a guard byte hardcoded to `F7h`. The pointer they form is therefore
`F7F7h`, and the dedicated `EI`/`RETI` stub was placed at exactly that address.
`F7F7h` is not an arbitrary choice: it is the address whose high and low bytes
are both the page-fill byte.

Moving the interrupt region moved the stub to `F717h` while the pointer still
resolved to `F7F7h` — which now lands inside the new driver slot. The existing
assertion did not catch it: it checks only that `irq_unexpected` still lives in
page `F7xx`, which remained true.

Re-establishing it means satisfying two constraints at once — the stub must sit
at an address ending in the page-fill byte, and the guard must equal that
address's high byte — or making both derived instead of hardcoded. That is a
small, careful piece of work whose only real verification is a hardware boot,
and it should not be done at the end of a long session.

**What is now known**, so the next attempt is short: twelve constants, one
solved blocker, one precisely characterised blocker, and an assertion that needs
strengthening because it passed while the invariant it guards was broken.

Reverted; the image is byte-identical to the running ROM and `make test` is 3/3.

### The consolidation, landed — CONSOLE=vdrip links for the first time

```text
F2F0h  SIO core            330 used (v9958) / 349 (vdrip) of 352
F450h  crossing layer       26 of 32      ROM_ACCESS_BASE moved to F462h with it
F470h  transport level       1 of 8
F478h  crossing gates      476 of 488
F660h  interrupt dispatch  189 of 248
F758h  COMMON DRIVER SLOT  384 reserved
F8D8h  headroom            128
F958h  staging buffer      unchanged
```

`CONSOLE=vdrip` produces a 512 KiB image. Its transport's interrupt half sits at
`F758h-F8BCh`, 357 bytes in the 384-byte slot with 27 spare; in a `v9958` build
the serial console tee's sink occupies the same slot with 300 spare. That is what
the slot is for: exactly one console driver's ISR-reachable half, whichever is
linked.

#### The FFh vector, now machine-checked

The blocker was a palindrome nobody had written down. An unclaimed bus supplies
vector `FFh`; the CPU fetches its pointer from `FDFFh` and `FE00h`. `FDFFh` is
not a byte anyone chose — it is the **high** byte of the vector page's last
entry, `irq_unexpected`. `FE00h` is a guard byte. So the stub they select must
sit at an address whose **low** byte equals `irq_unexpected`'s **high** byte.
`F7F7h` satisfied that by being the address whose two bytes are the same.

The old assertion only checked that `irq_unexpected` was still in page `F7xx`.
That stayed true when the region moved and the stub landed at `F717h` while the
pointer still resolved to `F7F7h` — by then somebody else's code. `make test`
caught it as *"ISR failed to return"*; nothing in the build did.

Now: the guard is derived (`.db (CBIOS_IRQ_FF_STUB >> 8)`), the stub's offset is
a named constant, and the identity is asserted in same-area arithmetic. Mutation
-tested — moving the offset by one byte fails the build with
*"FFh vector does not resolve to irq_ff_unexpected"*.

That invariant is also what caps the layout: the stub must be at `F6F6h`, the
code before it occupies exactly `96h`, so the interrupt region's base cannot
exceed `F660h` — and everything below is sized against that. 880 bytes for 852
of content.

#### Two things this turn also exposed

- **The SIO core is 19 bytes larger with `CONSOLE=vdrip`.** Sizing a region from
  one configuration is not enough; the first attempt overlapped the crossing
  layer in the VDrip build only.
- **Building a non-default configuration overwrites `docs/memory-map.md`.** The
  `--memory-map` path is not under `BUILD_DIR`, so `make BUILD_DIR=... CONSOLE=vdrip`
  silently replaced the checked-in map with the VDrip build's numbers. Worth
  fixing; for now, rebuild the default afterwards.

### Ready to flash

Default `make` clean, `make test` 3/3, `check_overlap` / `check_diag_record` /
`check_org_placement` all OK, and the FFh vector verified in the image itself:
`FDFFh`/`FE00h` form `F6F6h`, which is `irq_ff_unexpected`.

**This is the first change in this whole effort that is not byte-identical.**
Every address in common memory above `F2F0h` has moved. The harnesses cover the
interrupt core, the FAT BIOS and the FAT BDOS personality, but nothing here can
tell you the machine boots.

## 14. The VDrip console's ISR violated the placement rule

Symptoms reported: `CONSOLE=vdrip` fails its startup handshake roughly three
times in four, and crashes after a while when a program runs — SNTracker playing,
or SN2 starting. `CONSOLE=v9958` is unaffected.

### Cause

Both VDrip console receive paths, raw and framed, reach
`vdrip_call_raw_callback`, which does `jp (hl)` to a registered callback. That
callback and everything it touches were in **bank 7**:

```text
textq_put_ascii   4F50h   code the SIO0/B interrupt handler executes
textq_head        5341h
textq_tail        5342h   state it writes
textq_count       5343h
textq_buffer      5344h   128 bytes
```

Bank 7 is mapped only in mode 11. While an application runs, those addresses are
the application's own memory, so every byte from the proxy made the interrupt
handler execute and write the transient's memory. Load-dependent crashing
follows, and so does the startup race: cold boot crosses mode 10 several times
before reaching the CCP, and the handshake is exactly when bytes are flowing.

This is section 1's rule broken — ISR-reachable code and state must be in
common — and it predates this work. The driver has been at slot 0 in bank 7 since
the Phase 1/2 migration, and the configuration has not built since slot 5 was
reallocated, so it was latent and untestable. Making it link exposed it.

**The classification check could not catch it.** It validates declared regions
against the addresses they emit; this is reached through a function pointer
stored at run time. Indirect calls are a blind spot, and no amount of region
checking closes it.

### Fix

The interrupt half enqueues and returns; the foreground drains. Per the decisions
taken: drain in `CONST`/`CONIN`, and on overflow drop the byte so RTS
back-pressure holds the proxy rather than silently overwriting.

```text
common   vdrip_kbd_enqueue  + a 32-byte ring, head/tail/count   in the driver slot
bank 7   vdrip_kbd_drain    calls the registered callback, which lives here
```

`CONIN` drains on entry **and inside its wait loop** — it tests `textq_count`, so
a byte arriving after the first drain would otherwise sit in the ring forever.

The common driver slot grows 384 -> 432 bytes to hold the ring; headroom 80.

### Three mistakes worth recording

**A ring in the wrong window.** First placed with the transport's other state at
`CBIOS_VDRIP_TRANSPORT_WORK_AREA` — a 17-byte window inside the runtime state
block. The 35-byte ring ran over `sd_storage_unit`, `storage_caller_sp` and the
SIO and SERCON state. `check_overlap` said OK, because `.ds` reserves space
without emitting the bytes it compares. Moved into the slot with the ISR code.

**The drain was in common.** It calls the bank-7 callback, so it is foreground by
definition and belongs in bank 7. Having it in common cost slot space for nothing.

**`config.inc` could go stale, and that one is squarely mine.** Its rule depended
only on the Makefile, but its contents depend on `CONSOLE` and `FAT_BIOS_M1`,
which are command-line variables. A build in one configuration left a
`config.inc` that the next configuration assembled against — and `build/config.inc`
was found holding `VDRIP_TRANSPORT_LINKED = 1` in the default build directory,
which linked the VDrip transport's interrupt half into a v9958 build. The old
`sed` could not go stale because it rewrote the source every build. Now `FORCE`d,
written to a temporary file and moved only when the content changes.

The image already flashed and confirmed working is unaffected: the default build
is still `466ab0f3`, byte for byte.

## 15. Phase 5 closed — and one build-system defect that hid it

`CONSOLE=vdrip` boots. The test suite runs on it. It is slow, which is expected
of a console whose every glyph crosses a serial link, and is not being chased.

**What made it fit.** Not the contiguity reorder, which was believed to be the
prerequisite. The sink fix did it: making the RX ISR enqueue a byte and return,
as the project's own SIO rule always required, cut the common-resident part of
the transport from 357 bytes to roughly 44 plus the queue, which the existing
slack absorbed. The reorder was the expensive route to something a correctness
fix gave away. Step 6 of the analysis had already priced itself honestly at "64
bytes of extra contiguous headroom... a tidiness change, not a capacity one";
that assessment is now confirmed from the other direction.

**What hid it for three flash cycles.** `config/banks.ini` named its payloads
with literal relative paths (`path = build/bank7.bin`), which the image packer
resolves against the working directory. Every build therefore packed
`build/bank7.bin` whatever `BUILD_DIR` said. `tools/build_rom_disk.py` had the
same defect in `--chunk-prefix`'s default, which the Makefile never overrode, so
a `BUILD_DIR=elsewhere` build also wrote its ROM-disk chunks into the project's
`build/`, clobbering whichever configuration was there.

The VDrip ROM was verified by building into a clean directory and checking its
symbols. That build linked a correct VDrip bank 7 -- so the symbol check
passed -- and then packed the *V9958* bank 7 from `build/`. The burned image was
a hybrid: common memory from the VDrip link over bank 7 from the V9958 link, two
halves of an OS disagreeing about every address. minipro's "Verification OK" was
accurate; it verified the wrong bytes faithfully.

This also closes an earlier unexplained result in this log: the "dirty versus
clean `BUILD_DIR`" discrepancy of 3,564 bank-7 bytes was exactly this. The image
called correct at the time was the corrupted one.

Fixed: payload paths are written `${build_dir}/...` and expanded from a new
`--build-dir`; a `${build_dir}` with no `--build-dir` is a hard error rather
than a silent fallback; `--chunk-prefix` derives from `--image`'s directory; and
a `kind = boot` payload must live in the firmware's own directory, since it
comes from the same link. The default-directory image is bit-identical across
the fix, so nothing about normal builds changed.

`tests/fat_bios_m1.cpp` also still asked for `FAT_BIOS_M1_ENABLED`, renamed to
`FAT_DRIVE_ENABLED`, and failed `make test` with a bare `FAIL: map::at`.

**Lesson, in the same family as the others in this log:** every verification of
the VDrip build tested the link and none tested the artifact. The symbol check
proved the right driver was *linked*; nothing proved it was *in the image*. The
new boot-payload assertion is the check that would have caught it, and it is
structural rather than a measurement, so it cannot go stale.

### Steps 5.1 and 5.3 — will not be done

A decision, not a deferral. Drive A: is always the ROM disk. VDrip storage
existed because there was no SD card; there is one now, and A: holds the rescue
volume, which is the last place for a backend that needs a host proxy attached.
So `VDRIP_TRANSPORT_LINKED` keeps following `CONSOLE` alone, the
`STORAGE_A=vdrip requires CONSOLE=vdrip` error stays, and the four-way
`CONSOLE` x `STORAGE_A` matrix that was to be Phase 5's acceptance test is not a
meaningful test set. The two combinations that make sense are both confirmed on
hardware. The VDrip storage backend remains linked and may be retired outright
later.

## 16. Step 4.2 prep — the layout fictions retired, byte-identical

Analysis section 8.5 step 6 required this first: "~30 state constants including
live vestigial aliases from the flat design that should be retired first, as
their own byte-identical step." It was worth doing on its own merits, because the
address authority was asserting things that were no longer true.

Fifty-three constants removed, 588 to 535. Nothing referenced any of them
outside `memory.inc` except `CBIOS_DRIVER_SLOT0_BASE`, which stays -- it is the
one DRIVER_SLOT name that describes the banked design, 4800h in bank 7, where
both console drivers `.org`.

What they claimed, and what is actually there:

| Constant | Claimed | Reality |
|---|---|---|
| `CBIOS_DRIVER_SLOT1_BASE` | E400h, a driver slot | the CCP |
| `CBIOS_DRIVER_SLOT3_BASE` | EC00h, a driver slot | the BDOS facade |
| `CBIOS_DRIVER_SLOT4_BASE` | F000h, a driver slot | the BIOS tables |
| `CBIOS_DRIVER_SLOT5_BASE` | F680h, a driver slot | the interrupt dispatcher |
| `CBIOS_CODE_LIMIT` | common code ends at FA80h | it also runs at FC98h, FCE0h, FF60h-FFFFh |
| `CBIOS_SCRATCH_BASE/LIMIT` | FA80h-FDFFh is BIOS scratch | facade staging, facade copies, two interrupt islands, the IM2 vector page |
| `CBIOS_CORE_BASE/LIMIT` | F000h to E000h | a region of negative size |
| `CBIOS_CONSOLE_DRIVER_WORK_AREA` | FE80h, a driver work area | `CBIOS_ISR_SP_SAVE` |
| `CBIOS_V9958_CONSOLE_CODE_BASE` | "; E000h" | 4800h; the sibling alias was spelled `VDREP` |
| `RESERVED_*` (16) | build-time validation bounds | unreferenced; half pointed at the fictions above |

Two were worse than stale. `CBIOS_WORK_AREA`, which anchors twelve live runtime
state addresses, was defined as `CBIOS_SCRATCH_LIMIT` -- every piece of BIOS
state was addressed from the end of a scratch area that does not exist. It is now
anchored at `0xfe00` directly. And `CBIOS_CONSOLE_DRIVER_WORK_AREA` resolved to
`CBIOS_ISR_SP_SAVE`; a console driver that had taken the invitation would have
overwritten the interrupted stack pointer on every interrupt. It was never
referenced, so it never fired -- the same shape as the VDrip ring overrunning
the transport work area, and `check_overlap` is equally blind to it, because a
constant with no `.ds` behind it emits nothing to overlap.

The deletion set was computed, not eyeballed: a transitive unused-constant pass
over the whole repo. It reported 141 unused of 588; the other 88 are protocol
vocabulary (`FS2_*`, `IOC_*`, `ZSYSINFO_*`) that is deliberately complete, and
was left alone.

Verified: both configurations byte-identical, `make test` 3/3.

```text
build/zephyr80.bin                         unchanged (v9958, 466ab0f3)
build/bank7.bin                            unchanged
build/zephyr80-zcpr2-zsdos-vdrip-rom.bin   unchanged (0e613496, the burned image)
```

### The reorder itself is now a judgement call

With the prep done, what remains of 4.2b is moving code: gathering the zones
into disjoint ranges so free space in common is one block. The case for it has
weakened since it was written, and the numbers should be stated plainly before
anyone spends a flash cycle on it.

Against: its purpose was to make room for the VDrip ISR tail, and the sink fix
made that unnecessary. Step 6 priced the rest at "about 64 bytes of extra
contiguous headroom... a tidiness change, not a capacity one." It requires
moving the IM2 vector page, which changes the `I` register value, and the FFh
vector's palindrome constraint has to hold across the move -- that is now
derived and asserted rather than hardcoded, which is what makes the attempt
safe, but it is still the piece that broke the first attempt. Verification is a
hardware boot.

For: one honest headroom number that the build reports, and zones that are
actually disjoint rather than interleaved, which is what makes the placement
rule legible to the next person. Today `abi`, `crossing` and `interrupt`
alternate down the whole code area and three interrupt islands sit inside the
data region.

Not started. It is a decision about whether 64 bytes and legibility are worth a
flash cycle, and that is the user's call, not a technical blocker.

## 17. Step 4.3 — Z4 declared, and scattering made a build failure

The step was written as "size Z4 for the largest ISR tail." That part was
already true: the common driver slot is 432 bytes at F758h-F907h. What was
missing was everything that makes a zone a zone rather than an address.

### The gap: the slot's main occupant was unreported

`driver-isr` had exactly one region, the serial console tee, and it is
`optional=True` -- present only when `CONSOLE=v9958`. The VDrip transport's
ISR-reachable half, which is what the slot exists for, had **no region entry and
no ceiling constant**. `VDRIP_TRANSPORT_CODE_END` was referenced nowhere outside
the file that defines it.

So in the configuration where the slot actually carries a driver, `driver-isr`
reported zero runs, and nothing checked the sink against the slot's end. Step
4.4a's claim -- "every region in the system now has reserved slack rather than
inherited slack" -- had one exception, and it was the region that mattered most,
missed because it exists in only one configuration.

Declared now, and the measurement is worth recording:

```text
CONSOLE=v9958    84 used, 348 free
CONSOLE=vdrip   418 used,  14 free
```

14 bytes is the tightest margin in common memory. The comment on the slot had
estimated the VDrip half at "roughly 44 bytes plus a ring" -- written before the
region was measurable, and wrong by an order of magnitude, because 418 is the
whole ISR-reachable half: sink, keyboard ring and registration. Corrected in
place. Mutation-tested:

```text
ERROR: common VDrip transport sink: VDRIP_TRANSPORT_CODE_END = F8FAh exceeds
       CBIOS_VDRIP_TRANSPORT_CODE_LIMIT = F8E8h by 18 bytes
```

### The ratchet: no new code in holes

The zone machinery checked classification and said so in its own comment: "This
checks classification, not contiguity." That is the gap that lets a routine land
wherever a hole happens to be, which is how `interrupt` acquired islands at
FC98h, FCE0h and FF60h inside the data region.

Contiguity cannot be *required* without the reorder. It can be ratcheted.
`check_zone_fragmentation` counts the disjoint runs each common zone occupies,
by reserved extent rather than used bytes, and fails if the count rises:

```text
abi          4 runs   EC00-EF9F, F000-F1AF, F298-F2EF, F470-F477
crossing     4 runs   EFA0-EFFF, F1B0-F287, F450-F46F, F478-F65F
interrupt    5 runs   F288-F297, F2F0-F44F, F660-F757, FC98-FCFF, FF60-FFFF
driver-isr   1 run    F758-F907        <- required to stay 1
```

A count going *down* is the reorder making progress and reports a NOTE asking
for the baseline to be lowered. A count going up fails the build and names the
zone. `driver-isr` is stricter: it must be exactly one run, because a driver's
ISR-reachable tail belongs in the common driver slot or it does not belong in
common at all. Both branches mutation-tested:

```text
ERROR: common zone 'interrupt' now occupies 5 disjoint runs, up from 4: ...
       Something was placed in a hole rather than beside its zone; extend an
       existing run or move it to bank 7

ERROR: common zone 'driver-isr' must occupy one run and occupies 2:
       F758h-F906h, FF60h-FFFEh. A driver's ISR-reachable tail belongs in the
       common driver slot; the rest of the driver belongs in bank 7
```

The baselines hold in both configurations, so the ratchet is not
configuration-dependent.

Verified: both images byte-identical, `make test` 3/3. Nothing to flash.

**What this does and does not buy.** It does not un-scatter the three interrupt
islands; that is still the reorder. It stops the scattering growing, and it
makes the current fragmentation a number the build prints rather than a fact
you have to read the map to notice. The reorder's remaining value is now
precisely those four numbers going to 1, 1, 1, 1.

## 18. Step 4.4b — the blind spot, and where the slack actually needs to go

### A second unreported region, same shape as the VDrip sink

The bank-7 region table ran from the V9958 console ending at 5FFFh straight to
the banner printer at 8A00h. Between them, **10,752 bytes had no region and no
ceiling**: the drive tables, the resource pool, the 2 KiB font and the banner
text. The Data table documented them; nothing checked them.

Declared now, byte-identical:

```text
8000h-87FFh  Console font        asset  2048 used,   0 free
8800h-89FFh  Boot banner text    asset    64 used, 448 free
8A00h-8FFFh  Boot banner printer asset    56 used, 1480 free
```

That is the second time in two steps that the thing without a ceiling turned out
to be the thing someone wanted to grow. It is worth stating as a rule: a region
that exists only in one configuration, or that holds data rather than code, is
exactly the region that escapes the table.

### Bank 7 is not short of space; common is

```text
bank 7 unallocated    6510h-65FFh  240 | 6600h-7FFFh 6656 (pool) | D610h-DFFFh 10736
bank 7 in-region free 8391 bytes across 21 regions
common in-region free 14 bytes in the VDrip sink, 80 bytes of headroom at F908h
```

So the rebalancing 4.4b was written to do has little to buy. Nothing in bank 7
is pressing against a ceiling: the tightest is the SD backend at 23 free, and
the smallest, the ZSDOS BIOS table at 5 free, is a fixed-size structure that
does not grow. Moving bank-7 regions costs a flash cycle and risks the card
castle to redistribute slack nobody is short of.

**The one genuinely tight region in the system is in common and bank 7 cannot
help it**: the VDrip transport sink, 418 of 432 bytes. Immediately above it sits
the 80-byte block at F908h-F957h that memory.inc calls "the only free space left
in common."

### On the boot banner and the font

The banner is boxed in above by the FAT BDOS backend at 9000h, so it can only
grow downward, and the font is what it would grow into. That makes the two
observations one change: **the font's 2 KiB is the banner's only route to a
contiguous block bigger than 2 KiB.**

But it is probably not needed. Versions for the OS, BIOS and transport plus a
text logo fit in what is already reserved -- 448 free in the text region and
1480 in the printer, 1928 bytes without moving anything. The font move buys a
contiguous 8000h-8FFFh only if the logo is a bitmap.

And it buys nothing on space grounds: bank 7 has 17 KB unallocated. The font is
already ROM-resident in the sense that matters -- `bank7.bin` is a ROM payload
copied to SRAM 7 at cold boot, and the VDrip console already restores the atlas
from ROM bank 0 at `drivers/console/vdrip.asm:2680`. Making the V9958 path read
it from ROM on demand is a behaviour change to the boot path, to reclaim 2 KiB
in a bank with 17 KiB spare.

### Left open, deliberately

Two decisions, both costing a flash cycle, neither forced:

1. **Grow the common driver slot** from 432 to 512 bytes by raising its ceiling
   into the 80-byte headroom. The base does not move and nothing is placed
   relative to the ceiling, so it should be byte-identical. It takes the VDrip
   sink from 14 bytes of margin to 94, and spends the last general headroom in
   common on the one region that varies by configuration.
2. **Reflow 4000h-47FFh** so the SD backend's 23 bytes become ~535. Self
   contained: the block's outer bounds stay at 4000h and 4800h, four constants
   change, nothing outside moves.

## 19. Step 4.4b done — bank 7 on a uniform 512-byte granule

Every module in bank 7 now has a 512-aligned base and a size that is a multiple
of 512. The granule was the one settled in section 11 ("512; the population's
small end wastes most of a 1 KiB granule"), and it was applied to every module
rather than only the `driver` zone: boxing the core modules too costs about
2 KiB of waste in a bank with 17 KiB unallocated, and buys a rule with no
exceptions.

```text
3000h  512  ZSDOS BIOS table      4A00h  512  USB keyboard input
3200h  512  Console facade        4C00h  512  USB keyboard state
3400h  512  Storage facade        4E00h 1536  SD-card backend
3600h  512  VIDEO_SEND            5400h  512  B: select probe
3800h  512  IOCALL                5600h  512  Drive A: backend
3A00h 2048  IOC command lane      5800h  512  Drive dispatcher
4200h  512  Bulk entries          5A00h       spare 1536
4400h 1536  IOC bulk lane         6000h       data, unchanged

8000h 2048  Console font          A000h 6144  FAT BDOS backend
8800h 1024  Boot banner text      B800h  512  SIO services
8C00h 1024  Boot banner printer   BA00h  512  Serial console tee
9000h 4096  Console driver slot   BC00h  512  VDrip transport (bank 7)
```

### What it fixed beyond alignment

**A fourth unreported ceiling.** The console driver -- the largest module in the
system -- had its ceiling set to `VDRIP_STORAGE_DPHDPB_BASE`, the drive tables.
The biggest driver was bounded by a data structure that happened to follow it.
Step 4.4a missed it because the console region is built per configuration in
`CONSOLE_REGIONS` rather than listed with the others, which is the same reason
the VDrip sink and the VDrip bank-7 half were missed. Now
`CBIOS_CONSOLE_DRIVER_CODE_LIMIT`, mutation-tested.

**The VDrip transport's bank-7 half** had no region entry either. Third of
three. Declared: 297 of 512.

**A base that followed its neighbour's length.** `CBIOS_STORAGE_A_CODE_BASE` was
`CBIOS_SD_PROBE_CODE_BASE + CBIOS_SD_PROBE_CODE_SIZE`, so the A: backend moved
whenever the probe changed size. Absolute now.

**A dead linker flag.** `DRIVER_AREAS ?= -b DRV_STORAGE_A=0x4330` was defined in
the Makefile, referenced nowhere, and named no area that exists -- a leftover of
the abandoned relocation experiment. Harmless while dead, but `4330h` is now
inside the Bulk entries slot, so a future area of that name would have landed
there. Verified byte-identical with and without it, then removed.

### Verification

Every region: base 512-aligned, size a multiple of 512, and **used byte count
identical before and after in both configurations** -- the reflow moved modules
without changing their contents. `make test` 3/3. Payload provenance re-checked:
16 local VDP port writes in the v9958 image's bank 7, 0 in the VDrip image's.

Headroom that mattered: the Virtual Drip console goes from bounded-by-the-drive-
tables to 3309 of 4096, and the SD backend from 23 free to 791.

```text
build/zephyr80-zcpr2-zsdos-v9958-rom.bin   96f7765f75b7ec225dee92ee4f1e6c72
build/zephyr80-zcpr2-zsdos-vdrip-rom.bin   d61feff85f3839d5a2441e9d8cbde65e
```

**Both need a hardware boot.** This is the first change in the memory-model work
that moves code rather than declaring where it already is, so the checks that
passed are necessary and not sufficient.

Docs updated: the bank-7 ASCII map in `src/layout/memory.inc`, and the guide's
bank-7 diagram and driver-slot section, which still sent a new card author to

## 20. Step 4.2b — the contiguity reorder, and the end of the memory-model work

4.4b was confirmed on hardware first: the uniform-granule bank 7 boots. This
step then moved common memory, and it is the last one.

**Four zones, four runs, down from fourteen.**

```text
abi         1 run   EC00h-F1AFh   1456    was 4 runs
crossing    1 run   F1B0h-F4EFh    832    was 4 runs
interrupt   1 run   F4F0h-F84Fh    864    was 5 runs
driver-isr  1 run   F850h-F9FFh    432    was 1 run
```

`ZONE_RUN_BASELINE` is now 1/1/1/1, so the ratchet has become a plain rule: a
common zone occupies exactly one run, and the build says so if it ever does not.

### The dispatch block never moved, and neither did F6F6h

The earlier attempt failed on the IM2 `FFh` palindrome, and the assumption since
has been that consolidating Z3 means relocating the stub. It does not. Dispatch
does not have to be the last block in the zone:

```text
before dispatch:  CTC reset 16 + SIO core 352                  = 368
                  interrupt dispatch                             248   F660h-F757h
after  dispatch:  policy 72 + CTC mapping 32 + registration 144 = 248
```

`F660h` is exactly 368 bytes into the zone, so the dispatch block sits where it
always has, `irq_unexpected` is still `F6D7h` and the stub is still `F6F6h`. The
palindrome assertion passes without being exercised. Making it derived was still
the right fix -- it is what made the reorder safe to attempt -- but in the end it
did not have to bend.

### The two pieces of arithmetic that decided the layout

**Z1 closes without moving either anchor.** `EC00h` (the facade, and `FBASE` six
bytes in) and `F000h` (`CBIOS_BASE`) are both effectively pinned, leaving a
96-byte gap between them. The ABI surface's other two members -- the IOC link
failure record at 88 and the transport level byte at 8 -- are exactly 96.

**The data side is 16 bytes short, and that is structural.** The IM2 vector page
must be 256-aligned with its guard immediately after, and the state and stacks
follow it, which leaves exactly 160 bytes above them. The largest thing that can
be lifted into that space is the three small facade copies, 64 bytes; the ALV
copy is 256 and does not fit. So 96 bytes up there are unusable, and the code run
below is 16 bytes short of its 3600.

Those 16 came from `IRQ registration`, 160 reserved for 121 used, now 144 with 23
free -- the largest unused reserve among the regions that could give it up
without disturbing the dispatch block's position. Every other region kept its
reserved slack exactly. The old 80-byte headroom block is gone, replaced by 96
unallocated bytes at `FFA0h-FFFFh`.

### What the reorder broke, and what that says

Three build invariants and one test encoded the old geometry:

- `FACADE_CODE_LIMIT == CBIOS_SIO_QUIESCE_BASE` -- true only while a *crossing*
  region sat in the facade's tail. Now it must meet the IOC diag record.
- the facade-copy chain assumed all four copies formed one run below the vector
  page. They no longer do, so the check is now "no copy straddles the vector
  page, state or stacks."
- "facade stack overlaps IRQ registration code" -- registration used to live
  above the stacks because that is where a hole was. The check is now the
  opposite one: registration must stay out of the data region.
- `tests/irq_core.cpp` listed `F958h` as an address `irq_register_kernel` must
  refuse. `F958h` was the staging buffer and is now inside the common driver
  slot, so refusing it had become wrong. The *driver* was right the whole time --
  it derives its bounds from `CBIOS_BASE` and `FAC_BULK_BUF` and tracked the move
  by itself. Only the test hardcoded. It derives now too.

The pattern across this whole effort, one more time: **the checks that broke were
the ones written as literals; the ones written as relationships survived.**
